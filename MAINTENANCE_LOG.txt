QQ空间插件模块化维护日志
========================

项目目标
--------
从 Round 24 起，项目从单 main.py 拆分为多模块。每个模块文件保持 500-1000 行以内。

维护原则
--------
1. 保守修改，尽量不动已有功能，优先新增模块。
2. 每个 .py 文件保持 500-1000 行以内，职责单一。
3. import 保持一致：所有同级模块用 `from xxx import yyy`（无点前缀）。
4. 维护历史写本文件，不塞进 main.py。

新增功能：投稿审核（publish_review.py）
----------------------------------------
工作原理：
1. 普通用户发说说 → 走 LLM 审核
2. 关键词粗筛 → LLM 细审 → 审核通过才发布
3. 审核通过的内容自动加 "【来自 xxx 的投稿】" 标注
4. 管理员发说说 → 跳过审核，直接发布
5. 黑名单机制：
   - 违规一次记一次 strike
   - 累计超过 3 次（BAN_THRESHOLD）→ 永久拉黑
   - 拉黑用户无法再投稿
   - 黑名单存储在 publish_bans.db（独立的 SQLite 文件）
   - 黑名单不写在明文规则里（用户无感知）

新增管理员命令：
- /qq空间_封投稿 @用户 — 手动封禁用户投稿权限
- /qq空间_解封投稿 @用户 — 解封用户投稿权限
- /qq空间_审核状态 @用户 — 查看用户投稿违规次数

审核流程：
用户投稿 → 黑名单检查 → 关键词粗筛 → LLM 细审 → 通过/拒绝
  - 通过：自动加 "【来自 xxx 的投稿】" 标注后发布
  - 拒绝：记一次违规，累计 3 次后永久拉黑

Round 26 - 2026-06-08

目标：让投稿正文里的 @某人 变成 QQ空间蓝色可点击、会提醒对方的 @好友。

关键发现（钩子/格式）：
- 这不是单独的 API，而是正文 con 字段里的富文本标记：@{uin:QQ号,nick:昵称}
- 来源1：腾讯手Q空间接口文档 open.mobile.qq.com（TopicComment）：
  “@某人要转成 : @{uin:183852032,nick:diaodiao}”
- 来源2：QzoneExporter(template_filters.py) 解析历史说说同款正则：
  @\{uin:(\d+?),nick:(.+?),.*?\}

实现（utils.py 新增）：
- make_qzone_at / sanitize_qzone_nick：生成并清洗 @{uin:..,nick:..}
- build_at_map：从原生 At 段取 {uin:昵称}，昵称缺失时联网 get_nickname 补齐
- convert_ats_to_qzone：转 @QQ号 和 @昵称（仅限消息里真 @ 过的人）
- build_command_publish_text：斜杠命令按消息链位置重建正文并转换
- 防伪造：转换前把用户原文 @{ 打断成 @ {

接入（main.py）：
- /qq空间_发说说 改用 build_command_publish_text 重建正文
- llm_publish_feed 用 convert_ats_to_qzone 处理 LLM 传入的 text，并更新 docstring
  告诉模型可直接在正文写 @QQ号，无需自己拼特殊格式

已用纯函数单测覆盖：官方格式、@QQ号、@昵称、伪造打断、长数字不误伤、昵称含逗号/花括号清洗。

Round 27 - 2026-06-08
---------------------
线上报错：插件 astrbot_plugin_qqkongjian 导入失败：
  cannot import name 'build_command_publish_text' from 'utils'

根因：多文件插件用裸名 import（from utils import ...）。utils/config/db 等名字
通用，Python 的 sys.modules 是全局缓存：
  1) 热重载时旧版 utils 残留在 sys.modules → 新增函数导入不到（本次正是这种）；
  2) 跨插件同名 utils.py 互相顶替。
已用脚本复现出与线上完全一致的报错，并验证修复后导入成功。

修复（main.py 顶部，import 兄弟模块之前）：
- 确保本插件目录置于 sys.path[0]；
- 无条件 sys.modules.pop 掉这些同级模块名，强制从本插件目录重新读取最新文件。
这些模块都是无状态（只定义函数/类），重新导入安全。

关于“投稿可 @ 别人”：按用户要求不做限制——正文里的 @ 会变成
@{uin:..,nick:..} 蓝色可点击好友 @，且整条投稿本身仍带“【来自 @xxx 的投稿】”
归属标注，可追溯是谁投的，因此保持开放（可 @ 死党/情侣发生日祝福）。

============================================================
给后来 AI 维护者的避坑指南（务必先读，按踩坑概率排序）
============================================================
（这一节是经验沉淀，不针对某一个 Round。动手改之前花两分钟看完，能省几个小时。）

【坑 0】改完源码必须跑 build.py，否则线上根本没生效
- 本仓库是“多文件源码 + 单文件部署”双形态：开发改 *.py 源模块，
  但 AstrBot 实际加载的可能是 dist/main.py（build.py 合并产物）。
- 只改源码不跑 `python3 build.py`，等于没改。改完一定重新 build 并提交 dist/。
- build.py 的合并器很“朴素”：它逐行删除内部 import，**只认单行 import**。
  千万不要把 `from utils import (a, b, c)` 写成多行括号形式——合并时只删掉
  第一行 `from utils import (`，留下 `a, b, c)` 变成孤儿缩进，整个 dist 语法错。
  （Round 26 就栽在这，表现为 dist/main.py IndentationError。）
  → 同级模块 import 一律写成一行。

【坑 1】裸名 import + sys.modules 全局缓存 = 热重载/撞名炸弹
- 多文件插件用 `from utils import ...` 这种裸名导入。utils/config/db 名字太通用。
- Python 的 sys.modules 是进程级全局缓存：热重载时旧版模块会残留，新增的
  函数/类会“cannot import name xxx from utils”；别的插件同名文件也会互相顶替。
- main.py 顶部已加“兄弟模块隔离”：import 前把这些同名模块从 sys.modules 无条件
  pop 掉，并把插件目录顶到 sys.path[0]。**新增任何同级模块，记得把名字补进
  _SIBLING_MODULE_NAMES**，否则它又会重新踩这个坑。

【坑 2】审核/外部调用里，“系统错误”与“用户违规”必须分开
- 反例（已修）：LLM 审核 text_chat 超时/异常时返回 approved=False，上层当成
  内容违规 add_strike，3 次就把用户永久拉黑。用户什么都没做错却被 ban。
- 原则：凡是“流程没跑成功”（超时、provider 不可用、网络抖动）一律走独立的
  ERROR 分支——不记违规、不计阈值、不进冷却、提示稍后再试；只有模型明确判定
  “内容有问题”才计入惩罚。给惩罚类逻辑加错误分支前，先问“这是用户的错还是系统的错”。

【坑 3】发说说时不要用 event.message_str 取正文
- message_str 会丢掉 At 段（@某人）和图片等非文本组件，位置信息也没了。
- 要保留 @ 的位置并转成可点击好友，必须遍历 event.get_messages() 消息链，
  按段重建（见 utils.build_command_publish_text）。

【坑 4】任何要发到 QQ 空间正文的字符串都不可信，先清洗
- 正文里 @好友靠富文本标记 @{uin:..,nick:..}。如果直接把用户昵称/输入塞进去，
  用户可手敲 @{uin:任意号} 伪造 @ 别人，或用 {},换行 破坏标记结构。
- 已有防护：转换前把用户原文的 `@{` 打断成 `@ {`；昵称用 sanitize_qzone_nick
  清洗（去 {} 逗号 换行 CQ码）。投稿来源显示名同理走 _safe_attribution_name。
  新增任何“拼进正文/拼进接口”的字段，都要走清洗，别信群昵称。

【坑 5】QQ 空间接口本身很脆，别假设它稳定
- WAF 会对 msglist 类接口返回 501；h5 接口无有效 qzonetoken 会返回“使用人数过多”。
- delete 接口用登录账号自身 uin 构造 topicId，**只能删 bot 自己空间的说说**
  （撤回投稿正好够用）；跨账号删除做不到，鉴权要在上层按 interaction_log 判断。
- cookie/p_skey/g_tk 会过期，调接口失败先怀疑会话失效，不要一上来改业务逻辑。

【坑 6】改完怎么自测（沙箱里没有 astrbot/aiocqhttp，无法整体 import）
- 最低限度：对所有改过的文件 `python3 -m py_compile`，再 build.py 后对 dist 也编译一遍。
- 纯逻辑函数（如 @ 转换、昵称清洗）尽量写成不依赖 event 的纯函数，可直接单测。
- 想验证“模块加载链路/缓存问题”，可以 stub 掉外部依赖后用 importlib 复现（Round 27 用过）。

【坑 7】涉及惩罚/拉黑/封禁的阈值，改之前先想清楚误伤面
- BAN_THRESHOLD、冷却时间、每日限额这些数字背后是真实用户。
- 加新拦截规则时，优先“拒绝本次”而不是“累计惩罚”，把不可逆操作（永久拉黑）
  的触发条件收得尽量窄、尽量只由明确的人为违规触发。

【坑 8】方法名遮蔽内建类型 + 注解立即求值 = 类定义阶段炸
- 现象：导入插件报 TypeError: 'function' object is not subscriptable，
  栈停在某个 class 的某行类型注解（如 -> list[dict[str, Any]]）。
- 根因：PostDB 里有个方法就叫 list()。类体内一旦执行过 def list，名字 list
  在“类作用域”就被绑定成该函数，遮蔽了内建 list。若该 .py 顶部没有
  `from __future__ import annotations`，类型注解会在类定义时**立即求值**，
  在 def list 之后出现的 list[...] 注解就会去下标一个函数 → 报错。
  （Round 28：新加的方法注解恰好排在 def list 之后，于是触发。）
- 为什么 dist 不报、源码报：build.py 合并出的 dist/main.py 顶部统一有一行
  __future__ annotations，把全文件注解都变惰性；而多文件源码里 db.py 当时没有。
  → 教训：别假设“dist 编译过 = 多文件版也没问题”，两种形态都要验证。
- 修复：给所有源模块补 `from __future__ import annotations`（已全部补齐）。
  另外尽量别用 list/dict/type/id/filter 这种内建名当方法名/变量名。
- 自测要点：py_compile 只查语法，**不执行类体**，抓不到这个坑；必须真正
  import/exec 该模块（可 stub 掉外部依赖）才能在类定义阶段复现。

一句话总结：本仓库的暗坑集中在 ①双形态构建(build.py) ②裸名import缓存
③系统错误 vs 用户违规 ④不可信文本进正文。守住这四条，基本不会出大事。
